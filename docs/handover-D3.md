## 2. 产品是什么（给新会话的心智模型）

### 2.1 三个入口，一个内核

| 层 | 定位 | 说明 |
|---|---|---|
| 入口 A：粘贴检查 | **主战场** | 商家把已有文案贴进来检查（高频动作，一天 5–10 次） |
| 入口 B：从零生成 | 获客/体验 | 给没文案的人用；生成结果**必须经过自检 + 自动改写**才展示（ADR-003） |
| 内核 | 检索 → 检查 → 引用条款 → 逐条改写 → 人工确认 | 价值与护城河；**不是"多生成 10 版"** |

### 2.2 四条不能碰的铁律

1. **页面上的每个数字都必须来自后端**（`usage` / 历史条数 / 违规条数），不许写死、不许估（ADR-008）。
2. **改动条数 = 违规条数**，编号 ①②③ 三栏共用；改不了的逐条标「未自动改写」，**不编造**（ADR-009）。
3. **每条违规必须能指回原句 + 条款原文**（`clause` 来自 `rules.csv` 的 `quote`，逐字比对）。
4. **不展示无法定位的结论**：不再有「复检另有 N 处命中，需人工确认」这类没有落点的提示（ADR-009 修订）。

### 2.3 用户原话（理解产品的最好材料，都记在 `docs/log.md`）

- 「我们不可以因为有修改功能，就给用户专门挖坑……生成的东西就要一步到位。」
- 「系统只检查出 2 个问题，但是改的时候有三个问题蹦出来，这肯定是不科学的。」
- 「检查出来的就是确定有问题的，不要弄模棱两可的东西出来。」
- 「只要查过都要算在历史记录里，但是一定不要弄混了，每个人只能看到自己的记录。」

### 3.2 一次 analyze 的真实数据流（页面唯一入口）

```
POST /api/analyze  {content 或 draft_id}
  ├─ get_owner：读 X-Owner-Id（没有就落 "public" 桶）
  ├─ _resolve_and_check：建/取 draft（带 owner_id）→ check_text #1 → 写 checks 表
  ├─ check_text #2（独立样本）→ merge_check_results（去重 + 按原文位置排序）
  ├─ rewrite_draft(verify=False)：逐条替换 → changes（1:1，带 start/end）
  ├─ log_usage：一行 llm_usage 日志（tokens/耗时/attempts/owner）
  ├─ 写 events：kind=check，payload=完整响应快照（点开历史可恢复）
  └─ 返回 AnalyzeResponse
```

**注意**：`/api/check` 只检查（评测/外部接口用），页面**不再调用**；`/api/rewrite` 仍保留（带复检，给外部用），页面也不调用。

### 3.3 前端 `frontend/`

| 路径 | 职责 |
|---|---|
| `app/page.jsx` | 入口页：灰色占位示例、空着回车/点检查 = 用示例跑、最近记录（点击恢复）、生成表单 |
| `app/workbench/page.jsx` | 三栏工作台：**只渲染 sessionStorage 里的 analyze 结果**，不发改写请求 |
| `app/history/page.jsx` | 历史列表（标题/问题数/状态/时间，点击恢复） |
| `app/drafts/page.jsx` | 生成后的选稿页 |
| `app/rules/page.jsx` | 规则库（优先读真接口，后端没起才退回 7 条样例） |
| `lib/api.js` | 数据层：mock/真接口切换、字段归一化（ADR-006）、`X-Owner-Id`、非 JSON 错误兜底 |
| `lib/owner.js` | 匿名设备号（localStorage UUID） |

### 3.4 数据模型（6 张表）

- `products` → `drafts`（`owner_id` 可空，老数据为空）
- `checks`：每次检查的违规明细（`verdict` = violation / uncertain / suspected）
- `confirmations`：确认记录，`UNIQUE(draft_id)` 保证幂等
- `events`：**历史的主表**（方案 C）。`owner_id / kind / draft_id / title / violation_count / remaining_count / status / payload / created_at`
- `rules`：`rules.csv` 的副本，init 时重建

### 3.5 关键不变量（写新代码时必须守住）

1. `len(violations) == len(rewrite.changes)`，且 `n` 一一对应。
2. 每条 violation 的 `quote` 必须逐字出现在原文里（后端已校验，前端只做展示）。
3. 每条 violation 必须带 `clause`（条款原文）和 `source_url`。
4. `rewrite.changes[i].start/end` 切出来的文本 == `changes[i].after`（除 `unresolved`）。
5. 页面上的 tokens / 耗时 / 条数只能来自接口，不能有默认值兜底。
6. 所有读写按 `owner_id` 过滤；越权一律 404，不暴露存在性。

## 6. 下一步怎么做（核心）

### 6.1 评测集（预计 2 天，先做这个）

**为什么做**（和用户已经对齐过，别再重新论证）：

1. 没有评测就只能盲改：加规则/改 prompt 后不知道变好还是变坏；
2. 漏报分布决定补哪条规则，而不是拍脑袋；
3. 面试时"你怎么证明它准"要有话可说；
4. 但**不是**为了在简历上写一个漂亮的百分比——**自建小样本的数字要打折看，必须诚实标注局限**。

**三层样本，别混**：

| 层 | 内容 | 用途 | 进主指标？ |
|---|---|---|---|
| A 冒烟 | 明显违规的典型句子 | 证明链路没坏 | ❌ 太容易 |
| B 主指标 | 12–24 条**真实笔记** | 召回 / 误报 / 引用正确率 | ✅ |
| C 边界 | 拿不准、需要资质才能判的 | 单独分析，说明"为什么不判" | ❌ |

**gold 怎么定**（用户的核心顾虑：他的法律判断不够权威）：

- 不靠个人权威，靠**条款原文 + 正反例 + 双人一致**；
- 流程：我按条款预标注（rule_id + quote + 依据）→ 用户只做"同意 / 不同意（写一句理由）/ 拿不准"；
- 只有双方一致的进 gold；拿不准的进 C 层；
- 每个标签都能追到 `rules.csv` 的 `quote`，面试可复述。

**三个指标**：

| 指标 | 公式 | 备注 |
|---|---|---|
| recall | 命中的真违规 ÷ 全部真违规 | 漏报 |
| false_positive_rate | 误报条数 ÷ 模型报出的总条数 | 误报比漏报更伤信任 |
| citation_accuracy | quote 逐字命中原文 ∧ rule_id 存在 ∧ 条款原文与 rules.csv 一致 | **纯机器校验**，零主观 |

生成侧另有「人工过稿率」（1–5 分，≥4 算过），单独报告。

**文件与脚本**：

- 样本：`data/eval_cases/NNN-xxx.json`（已有格式：`id / split / brief / draft / ground_truth[] / expected_action / notes`，

  `author_verdict` / `author_note` 记录作者复核意见）、`negatives[]`（明确不该报的反例））。
  **不要放 `eval/`**：`.gitignore` 现已改为忽略 `eval/runs/`（B-009 已关闭；仍不要在 `eval/` 下放零散 JSON）。
- 脚本（已建，见 `eval/README.md`）：
  - `eval/import_inbox.py`：`data/eval_cases/inbox.md` → 样本 JSON（严格解析，占位符自动跳过）
  - `eval/label_sheet.py`：预标注 → `eval/label-sheet.md`（作者逐条勾「同意/不同意/拿不准」）
  - `eval/run_eval.py`：读样本 → 本地调 `analyze` → 三项指标 → `eval/results-v1.md`；`--from-raw` 可不调模型重算

  方法、样本来源、gold 规则、指标、错误分析（逐条列漏报/误报 + 根因）、局限）要等 12 条正式跑完再写。

- v1 基线：严格召回 2/8、提示召回 6/8、误报 5/7、引用 100%。
- v1.1（只改 prompt 判定纪律，规则/样本不动）：**严格召回 6/8、提示召回 7/8、误报 4/10、精确率 60%、引用 18/18**。
- 核心结论：瓶颈不是"看不见"，是"看见了不敢定"——4 处 gold 落在 `uncertain`（confidence 0.5–0.6），
  页面不展示；2 处是规则库没有「普通食品功效宣称」条款；1 处是 BM25 检索没召回。
- **对产品的直接结论**：先给 `uncertain` 一个展示出口（工作台"待确认"区）；v1.1 后报出量 10→18，
  用户更需要区分"确定违规"和"待确认"。
- **剩余问题**：014 方剂名仍漏（同类规则对 015 生效、对 014 不生效）；017 检索没召回 FLM-003；
  002 仍误报；新增 004/013 两条误报。
- 评测写独立 `eval/runs/<id>/eval.db`，不碰本地历史库；`--from-raw` 可零成本重算。

**下一步**：PRD（指标只引用 `report-v1.md`）→ 规则 v2（按 §5 缺口补）→ 补 8–10 条明显违规样本再跑一轮。

**报告写作要点**（面试官会怎么看）：

- 先写方法和局限，再写数字；
- 错误分析比总分更有价值：漏报是哪一类、为什么、补了什么规则；
- 不要写"准确率 95%"这种没有定义的数字。

### 6.2 PRD（预计 1 天）

**给谁看**：面试官 + 未来的自己。**一页纸为主**，不写成长篇小说。

**结构（建议）**：

1. **问题**：小商家没有专职合规；发布后被限流才知道；平台只说"涉嫌违规"，不说哪句、哪条。
2. **用户与场景**：1–3 人小商家；发布前自查；一天检查 5–10 次、生成 1–2 次。
3. **方案**：主路径粘贴检查 + 次入口生成；四步内核（检索→检查→引用→改写）+ 人工确认。
4. **关键决策**：直接引用 ADR-001/002/003/009（检查是内核、生成要自检、一次算完、数字可对账）。
5. **指标与评测方法**：三个指标 + 三层样本 + gold 规则 + 当前数字（来自评测报告）。
6. **边界与不做**：无登录（匿名设备号不是认证）、只查文本、40 条不是全量、不承诺平台一定通过、不直接发布。
7. **路线图**：规则扩容、账号级规则、多平台、图片/视频（都标 P2）。

**素材来源**：`decisions.md`（取舍）、`log.md`（真实反馈与事故）、评测报告（数字）、`backlog.md`（想清楚但没做的）。
**验收**：一个没参与的人 5 分钟能读懂"为什么做、怎么做、怎么衡量"。

### 6.3 再往后

1. **规则扩容**（评测驱动，45–50 条）：先看漏报分布，再找官方原文，跑 `verify_rules.py`。
2. **3 分钟视频**（用户录）：30 秒问题 → 90 秒演示（粘贴→检查→条款→改写→确认→历史）→ 30 秒取舍与边界 → 30 秒展望。
3. **简历条目**：写方法 + 一个具体发现，不吹百分比。
4. **HTTPS**（可选）：见 §7.4。

### 7.2 限流

- 配置：`deploy/nginx-content-guard.conf` 顶部 `limit_req_zone`；只作用于 generate/analyze/check/rewrite。
- 行为：每 IP 10 次/分钟，允许 9 次突发；第 11 次 429（JSON）。
- 验收：`deploy.md` §四之二 有 curl 命令（空 body 不花钱）。

### 7.3 备份与恢复

- 每日 03:00 → `~/content-guard-backups/content_guard-<时间>.db.gz`，保留 14 天。
- 脚本 `scripts/backup_db.sh`：SQLite 在线 backup API（WAL 安全）+ `integrity_check` + 打表行数。
- 恢复步骤写在 `docs/deploy.md` §四之二（先 stop 服务、备份现场、覆盖 db、删 `-wal/-shm`、start、健康检查）。

### 7.4 HTTPS（唯一挂着的部署项）

- 不紧急：域名只影响"链接观感"，不影响功能。
- 三条路：① 公网 IP 证书（Let's Encrypt 2026 起支持，**短期 6 天、必须自动续期**，仍需域名或 IP）；② 域名 + ICP 备案（上海机器，备案 1–3 周，需包年包月且剩余 ≥3 个月）；③ 换香港轻量服务器（免备案，月费 ¥24–40）。
- 用户已决定：**暂不做**，先补评测和 PRD。
- 若以后做：Nginx 加 `listen 443 ssl` + 80 → 301；前端不用改（同源相对路径 `/api`）。

### 7.5 本地开发

```bash
cd backend && .venv/bin/uvicorn app.main:app --port 8000     # 真后端
```

## 8. 坑（踩过的，按"会不会再踩"排序）

| 坑 | 位置 | 说明 |
|---|---|---|
| **Pydantic `response_model` 会裁掉没声明的字段** | `schemas.py` + `api.py` | 业务层算好了 `usage`/`clause`，schema 没声明 → 接口就是不返回。**加字段必须两边都改** |
| **Hook 不能在提前 return 之后** | `app/workbench/page.jsx` | 曾把 `useMemo` 写在 `if (!sample) return null` 后面 → React error #310 整页报错 |
| **mock 与后端字段名不一致 → 白屏** | `lib/api.js` | mock 用 `text`、后端用 `script`；必须在数据层归一化（ADR-006） |
| **`next build` 会清空 `out/`** | — | 临时 seed 页要在构建**之后**生成 |
| **粘贴文案的"标题"= 正文第一行** | `api.py` `_resolve_and_check` | 若同时当 title 传给检查器，同一句会查两遍；粘贴场景统一 `title=""` |
| **"改写后的复检"不能当结论** | `rewrite.py` / `api.py` | 它命中的句子可能在改写文里，指不回原句；已改为原文双检 + 逐条标注（ADR-009 修订） |
| **Nginx 429 默认是 HTML** | `nginx-content-guard.conf` | 前端 `JSON.parse` 会炸；已让 429 返回 JSON，前端也加了兜底 |
| **测试脚本自己会骗人** | — | 测备份保留策略时先 `touch -d` 又 `touch`，把 mtime 改回现在，误以为策略失效 |
| **服务器没有 `sqlite3` 命令行** | — | 用 Python `sqlite3` 模块（还能顺便做 integrity check） |
| **中文时间格式** | `page.jsx` / `history` | 后端返回 ISO（带 `T`），显示前 `replace("T"," ")` 再截 |
| **headless Chrome 要 `--user-data-dir`** | — | 否则报 `Failed to create headless user data directory container`，`--dump-dom` 为空 |
| **headless Chrome 最小视口 500px** | — | 390 宽截图不能判断窄屏溢出；要在页面里量 `innerWidth/scrollWidth` |
| **PDF 里的康熙部首字符** | `verify_rules.py` | `⻛/⻝/⻓` 与「风/食/长」码位不同；不映射永远匹配不上 |
| **端口被旧服务占用** | 本机 8000/8010/4321 | 先 `lsof` 看清楚是谁的，**别想当然 kill**（历史上误杀过一次预览服务） |

## 11. 用户偏好与约定（新会话请遵守）

1. **中文交流**；先讨论清楚再写代码，**不要边讨论边动手**。
2. **拒绝假数字**：所有展示的数字必须能对账（页面对 journalctl、对接口返回）。
3. **问题必须可定位**：每条违规要有原句 + 条款；不要"另有 N 处需人工"这种没有落点的提示。
4. **分批交付**：做完一批先给用户验收，再开下一批（用户明确要求过）。
5. **配色**：页面底 `#FFFAF0`、面板 `#FFFDF7`；不要纯白，不要改动色板除非用户要求。
6. **不要 AI 品牌露出**：状态条不显示模型名，工作台不写"AI 生成提示"（后端 `disclosure` 字段保留，前端不展示）。
7. **不做登录**：身份用匿名设备号；不要提议加账号体系。
8. **求职方向**：产品策划 / AI 产品 / 产品运营的**日常实习**（2027 届本科毕业，之后读研）。这个项目是**作品集**，所以"能讲清楚的方法与取舍"比"多一个功能"重要。
9. **评测要诚实**：自建小样本必须标注局限，不许在简历上写没有定义的百分比。
10. **用户不是法律专家**：标注时给条款依据，不要让他凭记忆判。
