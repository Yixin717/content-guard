## 1. 项目定义

### 1.1 一句话

> 把商家短视频带货文案的合规，从“发布后被限流”前移到“生成时就有护栏”，并且每条判断都能指回具体规则条款。

### 1.2 用户

- **主用户**：小红书中小商家 / 新品牌的内容运营（1–3 人团队）。
- **次用户**：代运营 / MCN 的内容编辑（同时服务 5–10 个商家）。
- **不是谁**：大品牌法务团队（他们有专门合规流程）、纯个人博主（付费意愿弱）。

### 1.3 痛点（待访谈验证）

1. 写完不知道会不会违规，只能发布后看结果。
2. 平台只给“涉嫌违规/限流”，不告诉你哪句话、违反哪条规则。
3. 改一版要 20–40 分钟，反复改 2–3 轮。
4. 小团队没有规则库，靠记忆、同行、零散工具查。
5. 不同平台规则不同，跨平台更麻烦。

### 1.4 价值

- **省时间**：把“写 + 查 + 改”从 1–2 小时压到 10–20 分钟。
- **降风险**：生成时就把高危词标出来，附条款和改写建议。
- **可追溯**：每条违规有 `rule_id` + 原文引用，方便复盘和团队交接。

### 1.5 差异化

| 现有工具 | 它做什么 | 它不做什么 |
|---|---|---|
| 零克查词等 | 查违禁词 | 不生成、不给改写、不引用条款 |
| 千瓜/新红 | 数据分析、达人筛选 | 不写、不查文案 |
| ChatGPT/普通 AI 文案 | 生成 | 不懂平台规则，容易违规 |
| 平台官方工具 | 有规则 | 只覆盖自家平台，不成工作流 |
| **本项目** | **生成 + 检查 + 引用 + 改写 + 人确认** | 不做真实发布、不做多租户 |

### 1.6 商业化（PRD 一页，不写代码）

- **定价**：按篇（如 1–3 元/篇）或订阅（如 99–299 元/月），代运营按坐席。
- **付费方**：商家老板 / 代运营负责人。
- **渠道**：代运营/MCN/服务商合作、免费合规检测引流、商家社群。
- **单位经济**：单篇模型成本 + 服务器分摊；目标毛利率 > 70%（按实际用量算，不编）。

## 3. 用户研究

### 3.1 用户画像（先写假设，访谈后改）

> 小林，28 岁，杭州，做小红书女装/健身服，团队 3 人：她负责选品和内容，一个客服，一个发货。每天发 1–2 条短视频带货，文案自己写。被限流过两次，不知道具体原因；现在写完会自己搜“违禁词”，但不系统。

### 3.2 要验证的 5 个假设

1. 商家最痛的是“不知道哪句话违规”，不是“不会写”。
2. 他们愿意为“少改两轮”付费，而不是为“多生成 10 版”付费。
3. 条款引用能显著增加信任（“它告诉我为什么”）。
4. 人工确认是必须的，全自动发布他们不敢用。
5. 代运营比单店商家更愿意付费（服务多个商家，复用规则）。

### 3.3 访谈对象与来源

- **目标**：5–8 位，20–30 分钟/位。
- **优先**：小红书/抖音/淘宝小卖家、代运营、内容创作者、本地商家（健身房/餐饮/工作室）。
- **来源**：
  - 朋友、同学、校友、家人。
  - 小红书/抖音私信（找 1k–5w 粉的小博主，说明“学生项目，20 分钟”）。
  - 闲鱼卖家（问“你写商品文案吗”）。
  - 本地商家（健身房、咖啡店、服装店，walk-in 或微信）。
  - 商家社群、知乎/小红书评论区。
- **替代**：找不到商家，就找 3 位创作者 + 3 位 proxy 小卖家 + 10 个公开案例。

### 3.4 访谈提纲（6 问，别问“你想不想要”）

1. 你现在怎么给商品写短视频带货文案？谁写？多久一篇？
2. 最近一次被限流/下架/改稿是什么情况？平台怎么通知你的？
3. 你怎么知道哪些词不能说？查什么工具？准不准？
4. 从写完到发布，中间要改几轮？最花时间的是哪一步？
5. 如果有个工具能“生成 + 检查 + 给改写建议”，你最想要哪个功能？最不信任什么？
6. 你现在为文案/合规花过钱吗？按篇还是按月？多少算合理？

### 3.5 如果找不到商家（Plan B）

- 写 1 页“我作为小红书用户/内容消费者的观察”，不装成商家访谈。
- 找 3 位创作者 + 3 位 proxy 小卖家，问同样的问题。
- 收集 20 个公开案例：限流/违规/改稿的帖子、平台处罚公告、商家吐槽。
- PRD 里诚实写：“6 位创作者/小卖家访谈 + 20 个公开案例；样本有限，结论待验证。”
- **不硬编“我访谈了 20 个小红书商家”。**

### 3.6 产出

- 1 页访谈笔记（每位 5–8 行）。
- 3 条原话（可直接进 PRD/面试）。
- 1 个痛点排序（按“痛 × 频率 × 愿付钱”）。
- 1 个用户画像（访谈后更新）。

## 4. 产品流程与三个核心场景

### 4.1 主流程

```
① 输入：商品名、品类、卖点、目标人群、价格、活动信息
② 生成：3 版短视频带货文案（痛点型 / 场景型 / 促销型）
③ 检查：规则检索 → LLM 逐条检查 → 违规项（rule_id + 原文 + 严重度 + 建议）
④ 引用：点开每条违规，看到规则原文与来源
⑤ 改写：按违规项生成合规改写，保留卖点
⑥ 确认：人工编辑/确认（不自动发布）
⑦ 导出：复制/下载 + 审计日志
```

### 4.2 三个核心场景

| 场景 | 内容 | MVP |
|---|---|---|
| **短视频带货** | 标题、口播脚本、卖点、行动号召 | ✅ 做 |
| **直播间话术** | 开场、产品介绍、逼单、答疑 | ❌ 只进 PRD |
| **商品卡/详情页** | 标题、卖点、参数、禁忌 | ❌ 只进 PRD |

### 4.3 为什么 MVP 只做第一个

- 文本、可评测、最像小红书笔记。
- 直播间话术是口语/实时，评测主观、演示难。
- 商品卡偏结构化，AI 含量低。
- 三个场景共用同一套规则引擎，PRD 里讲清“怎么扩展”就够了。

### 4.4 体验原则

- **不自动发布**：最后一步必须人工确认。
- **每条违规可点开**：原文 + 规则条款 + 来源。
- **改写保留卖点**：不能为了合规把卖点删光。
- **不确定就转人工**：检索不到依据时，不硬判“合规/不合规”。

## 5. 规则体系

### 5.1 三类规则（MVP）

| 类别 | 覆盖 | 例子 |
|---|---|---|
| **绝对化用语** | 广告法第九条 | 最、第一、国家级、顶级、极致、唯一、100% |
| **虚假宣传/医疗功效** | 广告法第十七/二十八条 | 治疗、治愈、根治、无效退款、纯天然、零风险 |
| **平台违禁词/引流/诱导** | 小红书社区规范/商家规则 | 站外引流、诱导互动、虚假种草、低俗、夸大对比 |

### 5.2 规则字段

```json
{
  "id": "ABS-001",
  "category": "absolute",
  "title": "禁止使用“最”类绝对化用语",
  "text": "广告不得使用“国家级”“最高级”“最佳”等用语。",
  "source": "《广告法》第九条",
  "platform": "xiaohongshu",
  "severity": "high",
  "examples": ["最好用的", "全网最低"],
  "version": "2026-10-24"
}
```

### 5.3 来源

- 《中华人民共和国广告法》第九条、第十七条、第二十八条。
- 小红书社区规范、小红书商家/蒲公英相关规则。
- 视频号运营规范、视频号小店规则（用于迁移页）。
- 公开处罚案例、商家吐槽（作为例子，不作为规则正文）。

### 5.4 版本与引用

- `rules.json` 带 `version`；每次更新跑一遍回归评测。
- 检查结果必须带 `rule_id` + `quote`（原文片段）+ `severity` + `suggestion`。
- 规则库不是法律意见；PRD 写明“仅供参考，最终以平台判定为准”。

### 5.5 边界

- 只做 3 类、30–50 条，不做全量。
- 不判断“会不会火”，只判断“是否违规/高风险”。
- 不替商家承担法律责任；输出是“建议 + 引用”。

## 6. 技术架构

### 6.1 架构图

```
浏览器
  │ HTTPS
Nginx (443)
  ├── 静态文件 ──> Next.js 静态导出（前端）
  └── /api/ ────> FastAPI (127.0.0.1:8000)
                     ├── 规则检索（BM25 + 类别）
                     ├── DeepSeek API（生成 / 检查 / 改写）
                     ├── SQLite（rules / drafts / checks / confirmations / eval）
                     └── eval 脚本（离线，跑 24 条）
```

### 6.2 为什么不用向量库

- 规则只有 30–50 条，BM25/关键词 + 类别检索足够。
- 全量规则入 prompt（约 3–5K tokens）比向量检索更稳，不会漏召回。
- 避免 embedding API/本地模型依赖，2 周更可控。
- 面试话术：“不是所有检索都要向量库；规则少时，可解释的 BM25 更合适。”

### 6.3 为什么不用 Agent

- 合规要可审计、可复现、可追责；固定流水线 + 人工确认更稳。
- Agent 的自主性在这里是风险：它可能跳过检查、改错、或“自作主张”。
- 面试话术：“这个场景不该用 Agent；该用一条可回放的流水线。”

### 6.4 RAG 的最小实现

- 规则/商品资料 → 按条款/段落切分 → 建 BM25 索引 → 检索 top-k → 与商品卖点一起进 prompt → 输出带 `rule_id`/`quote` 的结果。
- 不写“向量检索”，除非真的用了 embedding；简历写“BM25 规则检索 + 引用回溯”。
- 如果时间够（P2）：加商品资料 PDF/Word 上传，做“文档切分 + BM25”，让 RAG 更完整。

### 6.5 模型与成本

- 模型：DeepSeek `deepseek-chat`；JSON 输出；失败重试 2 次。
- 记录每次调用的 `tokens_in/tokens_out/latency/cost`。
- 评测里算“单篇成本”和“p50/p95 时延”。
- 不在简历里写“成本降低 X%”，除非有真实对比。

### 6.6 前端

- Next.js 静态导出；3 个页面：
  1. **工作台**：输入 → 3 版草稿 → 违规列表 → 引用抽屉 → 改写 → 确认 → 导出。
  2. **历史**：已确认的文案 + 审计日志。
  3. **规则/评测**：规则列表 + 评测指标（读 JSON）。
- 状态：loading、空态、错误、重试；移动端至少能看。

### 6.7 部署

- 腾讯云 CVM（Ubuntu 22.04/24.04）。
- Nginx：静态 + `/api/` 反代；80 → 301 → 443。
- systemd：`content-guard.service`，`Restart=always`。
- SSL：腾讯云免费证书（比 certbot 更贴腾讯云）。
- 安全组：22/80/443；关闭 8000。
- 环境变量：`.env`（不进 git），`.env.example` 进 git。

### 6.8 测试与 CI

- pytest 5 条：
  1. `/api/generate` 参数缺失 → 422。
  2. `/api/check` 空文本 → 422。
  3. 规则检索返回正确类别。
  4. LLM 返回坏 JSON → 重试/降级。
  5. `/api/confirm` 幂等（重复确认不重复写）。
- GitHub Actions：ruff + pytest。
- 不追求覆盖率；追求“失败路径有测试”。

## 7. 数据模型与接口

### 7.1 表

| 表 | 字段（最小） |
|---|---|
| `products` | id, name, category, selling_points, audience, price, created_at |
| `drafts` | id, product_id, version, angle, content, status, created_at |
| `checks` | id, draft_id, rule_id, quote, severity, suggestion, created_at |
| `rules` | id, category, title, text, source, platform, severity, version |
| `confirmations` | id, draft_id, final_content, reviewer, created_at |
| `eval_cases` | id, split, brief, draft, ground_truth_json, expected_action |
| `eval_runs` | id, model, prompt_version, recall, false_positive, citation_accuracy, cost, latency, created_at |

### 7.2 API

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/generate` | `{brief, platform, tone}` | `{drafts: [{id, angle, content}]}` |
| POST | `/api/check` | `{draft_id}` 或 `{content}` | `{violations: [{rule_id, quote, severity, suggestion}]}` |
| POST | `/api/rewrite` | `{draft_id, violation_ids}` | `{rewritten, diff}` |
| POST | `/api/confirm` | `{draft_id, final_content}` | `{ok, audit_id}` |
| GET | `/api/history` | `?limit=20` | `{items: [...]}` |
| GET | `/api/rules` | `?category=` | `{items: [...]}` |
| GET | `/api/eval/summary` | — | `{recall, false_positive, citation_accuracy, cost, latency}` |
| GET | `/health` | — | `{status: "ok"}` |

### 7.3 错误处理

- 参数校验：Pydantic，长度/枚举/必填。
- LLM 超时：504 + 重试 2 次 + 前端提示“转人工”。
- LLM 坏 JSON：重试 + 解析兜底 + 记录失败样本。
- 规则无命中：返回“未发现明确违规，建议人工复核”，不硬判合规。
- 幂等：`/api/confirm` 用 `draft_id` 去重。

## 8. 评测方案

### 8.1 评测集

- **24 条**：16 条开发集（dev）+ 8 条留出集（test）。
- 其中 **18 条含违规**（3 类各 6 条），**6 条干净/模糊**（3 干净 + 3 模糊/超范围）。
- 每条包含：
  - `id`, `split`, `brief`, `draft`
  - `ground_truth`：`[{rule_id, quote, severity}]`
  - `expected_action`：`block` / `warn` / `pass` / `human_review`
  - `notes`：为什么这么标

### 8.2 指标

| 指标 | 公式 | 目标 |
|---|---|---|
| 违规召回率 | TP / (TP + FN) | ≥ 85% |
| 误报率 | FP / (FP + TN)，干净样本上 | ≤ 15% |
| 引用正确率 | 正确 rule_id + quote 重叠 / 总违规 | ≥ 90% |
| 人工过稿率 | 评分 ≥ 4/5 的比例 | ≥ 80% |
| 单篇耗时 | 从输入到确认 | 记录实际值 |
| 单篇成本 | tokens × 单价 | 记录实际值 |
| 时延 | p50 / p95 | 记录实际值 |

> 目标不是保证，是“先定标准，再看实际”。报告里写真实数字，不达标就分析原因。

### 8.3 防过拟合

- 只在 **16 条 dev** 上调 prompt/规则/检索。
- **8 条 test 冻结**，调完再跑一次；看到结果后不再改。
- 报告里分开写 dev / test；不要只报 dev。
- 如果时间够，扩到 30 条（20 dev / 10 test）。

### 8.4 人工评估

- 2 位评审（你 + 1 位朋友/同学），1–5 分：
  - 这条文案能不能直接发？
  - 改写有没有丢掉卖点？
  - 引用是否让你相信？
- 算简单一致率；不一致的 case 单独讨论。
- 如果能找到 2–3 位商家试用，记录原话，不进“准确率”，进“定性反馈”。

### 8.5 报告结构

1. 评测集构成（多少条、怎么标）。
2. 总体指标表（dev / test 分开）。
3. 分类指标（3 类规则各自召回/误报）。
4. 3 个成功案例（输入 → 检出 → 引用 → 改写）。
5. 3 个失败案例（漏检/误报/引用错/改写丢卖点）。
6. 失败模式归类 + 下一步。
7. 局限：24 条样本小、规则库不全、平台规则会变。

## 14. 面试 3 分钟讲法 + 追问

### 14.1 3 分钟脚本（背下来）

> 小红书商家做短视频带货，文案要同时满足“能卖货”和“不违规”。但 1–3 人的小团队没有专职合规，通常是写完再查、查完再改，还是会被限流或下架。
>
> 我做了个商家内容合规与生成助手：输入商品卖点，生成 3 版短视频带货文案，同时按平台规则和广告法检查，每条违规都指回具体条款，给合规改写建议，最后必须人工确认才导出。
>
> 我用 24 条评测集测，其中 8 条是留出的；违规召回率 X%，误报率 Y%，引用正确率 Z%，单篇生成+检查耗时 A 秒。
>
> 我故意不做自动发布，也不做自主 Agent——合规场景要的是可审计的固定流水线 + 人工确认，不是让模型自己决定发什么。
>
> 这个产品第一个适配小红书，但规则层和平台适配层是分开的，下一步可以接视频号小店/直播/商品卡；腾讯生态里商家内容合规是共性需求。

### 14.2 十个追问

1. **为什么不用 Agent？** 合规要可审计、可复现、可追责；固定流水线 + 人工确认更稳；Agent 的自主性在这里是风险。
2. **为什么不用向量库？** 规则 30–50 条，BM25/类别检索足够；全量规则入 prompt 更可靠；避免 embedding 依赖。
3. **误报怎么办？** 分级（高/中/低）+ 人工确认 + 误报反馈进规则库；评测看误报率。
4. **规则更新怎么办？** 规则库版本化；每次更新跑回归评测；平台 adapter。
5. **商业化？** 按篇/订阅/服务商分成；先做工具，后做团队协作。
6. **增长？** 服务商/代运营渠道；免费合规检测引流；报告分享。
7. **腾讯生态？** 视频号小店/直播/商品卡/企微/腾讯广告；规则和内容形态变，workflow/评测不变。
8. **你的角色？** 独立完成需求/访谈/PRD/规则/评测/前后端/部署；AI 辅助编码，但每行能解释。
9. **如果重来？** 扩大评测集、加规则版本管理、加团队协作、做视频号 adapter。
10. **数据隐私？** 合成数据；公开案例脱敏；不存商家敏感信息。

### 14.3 如果被问“为什么不做视频号”

> 我每天用小红书，对内容风格和违规边界有直觉；视频号我还没用过，公开资料也少。但产品架构是平台无关的：规则层和适配层分开，PRD 里专门写了视频号迁移页。先用小红书验证 workflow，再接视频号，是我认为 2 周内更稳的顺序。

## 16. 腾讯云部署清单

### 16.1 服务器

- CVM：Ubuntu 22.04/24.04，2C2G 起。
- 安全组：22（你的 IP）、80、443；**关闭 8000**。

### 16.2 域名与 SSL

- 域名 A 记录 → CVM 公网 IP；`www` 可选。
- 腾讯云免费 SSL 证书（DV），下载 Nginx 版。
- Nginx：443 ssl；80 → 301 → https。

### 16.3 Nginx（示意）

```nginx
server {
    listen 80;
    server_name your-domain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate     /etc/nginx/ssl/your-domain.pem;
    ssl_certificate_key /etc/nginx/ssl/your-domain.key;

    root /var/www/content-guard;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 16.4 systemd（示意）

```ini
[Unit]
Description=content-guard backend
After=network.target

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/content-guard/backend
ExecStart=/home/ubuntu/content-guard/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=always
EnvironmentFile=/home/ubuntu/content-guard/backend/.env

[Install]
WantedBy=multi-user.target
```

### 16.5 验证

- `curl https://your-domain.com/health` → `{"status":"ok"}`。
- 公网访问 `http://IP:8000` → 连不上。
- `sudo kill <PID>` → `systemctl status` 还是 running，PID 变了。
- 手机 4G 打开 demo。
