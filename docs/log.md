## 追加 · 2026-10-25（线上崩溃修复）

**事故**：手机打开工作台，点了几下后白屏 → `Application error: a client-side exception`。

**根因**：mock 里改写结果字段叫 `text`，真实接口叫 `script`。
`rw.text` 为 undefined，`rw.text.indexOf(...)` 直接抛错，整棵树崩掉。

**修法**
1. `lib/api.js` 增加 `normalizeRewrite` / `normalizeDraft`：**在数据层把两种形状抹平**，UI 不再关心后端字段名。
2. 工作台防御式渲染（`rw?.text || ""`）。
3. 新增 `app/error.jsx`：以后出错显示中文提示 + 重试/回入口，**不再是黑屏英文**。

**顺带修的移动端**：三栏堆叠后每栏仍是 `overflow-y:auto` 且被网格压成固定高度，内容被截断 →
改为 `height:auto` + `overflow:visible` + 整页滚动。

**一条排查记录**：用 390px 宽截图一直看到"右侧被裁"，以为是布局问题；
实测 `innerWidth=500`（headless Chrome 有最小视口 500），390 截图是"500 渲染 + 390 裁剪"的假象。
**结论：headless 截图不能用来判断窄屏溢出，要用 `innerWidth/scrollWidth` 实测。**

## D2 追加 · 2026-10-25（干掉假数字：B-008）

**背景**：交接文档把状态条的 `tokens 9,254 / 1,198`、`15.7s` 列为最危险的 bug。动手后发现原计划（"只改前端读接口 usage"）做不成，因为：

1. 状态条在工作台，但一次任务跨 `/api/check` + `/api/rewrite` 两个请求；
2. 这两个接口的 `response_model` 里没有 `usage` 字段，业务层算好的数字在接口边界被裁掉了；
3. `/api/generate` 只累加写作调用，自检/改写/复检的 token 全没算；
4. `api.py` 没有任何日志，原验收标准"与 journalctl 一致"根本无法执行。

**做了什么**（ADR-008）
- 后端三接口全部返回 `usage`（tokens / llm latency / 请求耗时 / 调用次数）；改写算上前置检查与复检，生成算上自检与自动改写（3 版最多 12 次调用）。
- 每次请求打一行 `llm_usage path=… tokens_in=… elapsed_ms=…` 到 stderr，日志器自带 handler，不依赖 uvicorn 配置。
- 前端 `lib/api.js` 透传、`lib/usage.js` 相加；`StatusBar` 删掉默认值，没有数字就不显示；工作台显示"本次任务合计"。
- 首页「最近」改读 `GET /api/history`（标题 / 来源 / 确认时间），删掉静态 `RECENT`。
- 顺手清掉 git 里误跟踪的 `data/content_guard.db-wal`、`.db-shm`，`.gitignore` 补 `*.db-wal/-shm/-journal`。
- 新增 4 个测试，后端 14 → 18 passed。

**怎么验的**
- 后端测试断言调用次数：改写 = 3 次（前置检查 + 改写 + 复检）、生成 = 12 次（3 版 × 4）。
- 前端不容易测，就起了个**桩接口**（不调模型、数字很好认）重建静态导出，用无头 Chrome 跑真实页面：
  check `1234/210`（1.5s）+ rewrite `800/150`（1.1s）→ 工作台状态条显示 `tokens 2,034 / 360`、`耗时 2.6s`；`/drafts` 显示 `tokens 4,321 / 777`、`耗时 12.3s`。
- `grep -rn "9,254\|15.7s" frontend/` 无结果。

**踩到的坑**
- 本机 8000 / 8010 端口都有旧的 uvicorn 在跑，桩服务绑不上；换成 8791 才干净。**那两个后端跑的是旧代码，要重启才有 `usage` 字段。**
- 真实 `/api/history` 的 `created_at` 是 ISO 格式（带 `T` 和时区），直接 `slice` 会显示出 `10-24T17:26`；要先把 `T` 换成空格再截。
- 为了看效果我随手起了个 4321 静态预览，结果绑失败、把**原本就在跑的那个**当成自己的 —— 后来按文档里的命令重启恢复，并重新用默认（mock）配置构建了 `out/`。

**部署与线上对账（当天 16:11 完成）**

## D2 追加 2 · 2026-10-25（第一批：一次算完、条款原文、配色、去 AI）

**用户反馈（原话）**
- 中栏「条款原文」是空的；
- 首页不能上下滑动、历史不更新；
- 每次进来都是那段示例文案；
- **检查出 2 处，改写冒出 3 处，数量对不上**；
- 右侧改写文里没标出哪里被改了；
- 首页和检查页底色差太多；清空页偏白想再暖一点（给了 `#FFFAF0`）；
- 不想让人看出是 AI 生成的（状态条 `deepseek-chat`、AI 标注提示）。

**根因（都是数据链路问题，不是样式）**
1. `ViolationOut` 没声明 `clause`，Pydantic 把条款原文裁掉了；
2. 检查与改写是两个请求，`/api/rewrite` 内部**又查了一遍**，两次结果可能不同 → 数量对不上；
3. 「改动明细」直接来自模型自述的 `changes`，模型会顺手多改；
4. 右栏高亮逻辑依赖 `changes[].n`，后端不返回该字段 → `p.n` 为假 → 整段按纯文本渲染；
5. 首页 `.main` 没有滚动容器，只有窄屏才给 `overflow`。

**做法（ADR-009）**
- 新增 `POST /api/analyze`：检查 → 逐条改写 → 复检，**全部算完才返回**；
- 改写改成**逐条局部替换**：模型只回答"这条违规换成什么"，替换由服务端执行并算出 `start/end`；
- 改动条数 = 违规条数，编号三栏共用；改不了的标 `unresolved`「未自动改好」；
- 违规项带 `clause` / `source_url`，中栏直接显示条款原文与建议改法（删掉假的「看条款」）；
- 右栏改动处 = 蓝字 + 浅蓝底 + 下划线 + 小序号；
- 状态条删掉模型名与写死的规则分档；配色统一 `#FFFAF0` / 面板 `#FFFDF7`；主区可滚动 + `100dvh`；
- 首页示例改为灰色占位，空着回车/点检查 = 用示例跑；「编辑原文」回填上次文本。

**验收**
- 后端 22 passed（断言：改动条数 = 违规条数、`start/end` 切片等于 `after`、改不了时标 unresolved 且 remaining 如实为 1）；
- 线上实测：4 处违规 → 4 条改动，编号 1:1，`start/end` 全部命中；usage `5817/689`、3 次调用、5.2s；
- `journalctl -u content-guard | grep llm_usage` 有 `path=/api/analyze … violations=4 rewritten=1`；
- 桩接口 + 无头 Chrome 验证过：条款原文有内容、改动明细条数一致、高亮 3 处、状态条数字为真。

**踩到的坑**
- React error #310：`useMemo` 写在了 `if (!sample) return null` 之后，hook 顺序不一致 → 整页报错。**所有 hook 必须在提前 return 之前**。
- `next build` 会清空 `out/`，之前放的 seed 页会被删掉，要在构建**之后**再生成。
- 粘贴文案的"标题"就是正文第一行，若同时当 `title` 传给检查器，同一句话会被检查两遍（改写还可能只改到 title、正文没变）→ 粘贴场景统一 `title=""`，只查正文。

**下一步**：第二批（历史记录 + 匿名设备号，方案 C 事件表）。

**验收后修订（21:20）**
- 用户反馈：问题顺序不是按原文从上往下 → `check_text` 改为**按 quote 在原文中的位置排序**（同位置再按严重度），编号 ①②③ 与阅读顺序一致；补一条反序返回的测试（23 passed）。

- 每个人只能看到自己的记录；
- 数据库方案在 A/B/C 里选了 **C（事件流）**，身份用**匿名设备号**；
- 历史列表只要「标题（或首句）+ 时间 + 几处问题」；点开能恢复那次任务。

**做法（ADR-010）**
- 新增 `events` 表：`owner_id / kind / draft_id / title / violation_count / remaining_count / status / payload / created_at`；
  `payload` 存当次 analyze 快照，点开直接恢复工作台；确认时把该草稿最近一条标 `confirmed`。
- 匿名设备号：`lib/owner.js` 生成 UUID 存 `localStorage`，`api.js` 统一加 `X-Owner-Id` 头；不用 cookie（本地跨端口会被 SameSite 拦）。
- `drafts` 增加 `owner_id`（老库用 `PRAGMA table_info` + `ALTER TABLE` 补列），生成/粘贴建档时写入。
- 越权一律 404：别人的 `draft_id`（检查/确认）和别人的 `event_id` 都不暴露存在性。
- 老数据 `owner_id` 为 NULL：不归属任何人，也不出现在列表里（符合"让它消失"的决定）。
- 前端：首页「最近」显示标题 + N 处问题 + 时间，点一条直接恢复；历史页加状态标签（未确认/已确认）与「查看全部」。

**验收**
- 后端 28 passed：同设备查两次两条、另一设备为空、别人的 event 404、确认后状态变 confirmed、别人不能用自己的 draft。
- 本机起了真 FastAPI + 假模型（临时库）用 curl 走了一遍同样的链路，结果一致。
- 前端用桩接口验证：A 设备首页两条记录、B 设备显示「还没有记录」；历史页标签与时间正常。

**边界（必须写进 PRD）**
- 换浏览器/清缓存看不到旧记录；
- 伪造 `X-Owner-Id` 能看到别人的记录 —— 不是安全边界，只是隔离命名空间。

**下一步**：限流 + HTTPS 前置（域名还没定），再往后是评测集 12 条。


**验收后修订 2（21:40）：不再出现"复检另有 N 处"**

- 用户反馈：这句不专业，也没说去哪检查；"检查出来的就是确定有问题的，不要模棱两可"。
- 根因：复检跑在**改写后的文本**上，命中的句子很可能不在用户原文里 → 指不回原句、标不出位置。
- 改法：`analyze` 改为**对原文做两遍独立检查、取并集去重**（每条都能标位置、带法条），改写只针对这份并集；不再把改写后的复检当结论（`verify=False`），响应里也不再有悬空的 `remaining`。生成流程的自检门禁保持不变。
- UI：删掉"复检另有 N 处命中"和那句防御性说明；表头改成"X 处已改写（· Y 处需手工）"；逐条仍是"未自动改写"。

## D2 追加 4 · 2026-10-26（工程收尾：限流 + 备份）

**为什么现在做**
公开站点 = 公网 IP + 无登录 + 每次请求花钱；SQLite 只有一个文件、没有备份。这两件都不影响功能，但出事就救不回来。

**限流**
- 只挡会调模型的四个接口（generate/analyze/check/rewrite），历史/规则/确认/健康检查不限。
- 每 IP `10r/m` + `burst=9 nodelay`：连发第 11 次开始 429；429 也返回 JSON，前端显示"请求太频繁了"。
- 实测：连发 12 次，前 10 次 422（空 body 校验），第 11/12 次 429，响应体正确；同时 history/rules/health 仍 200。

**备份**
- `scripts/backup_db.sh` 用 SQLite 在线 backup API（WAL 安全），备份后 `integrity_check` + 打表行数，gzip 存 `~/content-guard-backups`，保留 14 天。
- `/etc/cron.d/content-guard-backup` 每天 03:00；`deploy.sh` 每次部署先跑一次。
- 实测：备份可解压、可打开、`integrity: ok`，行数与线上一致；造一个 20 天前的备份验证了清理策略；恢复演练通过。

**踩到的坑**
- 保留策略测试第一次没生效——先 `touch -d "20 days ago"` 又 `touch` 了一次，把 mtime 改回现在。**测试脚本自己也会骗人。**
- 服务器没有 `sqlite3` 命令行，只能用 Python 的 `sqlite3` 模块（反而更好，能自带 integrity check）。
- Nginx 的 429 默认是 HTML，前端 `JSON.parse` 会直接抛错；必须让 429 也返回 JSON + 前端兜底解析。

**已知边界（写进 PRD）**
- 备份与数据库同机，整机故障会一起丢；异地备份未做。
- 限流按 IP，同一出口 IP 的多人共享额度。
- 没有告警，备份/证书失败只能看日志。

**下一步**：评测集 12 条 + 第一轮指标（HTTPS 等域名决策，暂挂）。
