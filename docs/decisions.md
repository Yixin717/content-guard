## ADR-001 · 产品内核是「检查与修订」，不是「生成」

**日期**：2026-10-24（D1）
**状态**：已采纳

### 背景

D1 的 CLI 已经能一次生成 3 版文案并逐条检查。由此产生一个必须回答的问题：
这产品到底是"帮商家写文案"，还是"帮商家看文案有没有违规"？

### 决策

**两条腿，但只有一个内核：**

| 层 | 定位 | 作用 |
|---|---|---|
| 入口 A：从零生成 | **获客/体验** | 让"合规"在生成时就发生（护栏前移），而不是事后补救 |
| 入口 B：粘贴已有文案检查 | **主战场** | 商家真实场景：文案多半是手写或改自详情页，不是每次从零生成 |
| 内核：检索 → 检查 → 引用 → 改写 → 确认 | **价值与护城河** | 别家只做其中一段；这里做完整条链且可追溯 |

### 理由

1. **生成不是瓶颈，证据来自自己的实测。** D1 用真实 brief 跑，三版草稿**全部零违规**——说明只要 prompt 里把规则写清楚，模型已经能守住底线。既然如此，"能生成"本身不构成差异。
2. **用户不会为"多生成 10 版"付钱，会为"少改两轮"付钱。**（对应计划 §3.2 假设 2）改一版 20–40 分钟、反复 2–3 轮，这才是成本所在。
3. **单做检查会退化成查词工具。** 零克查词那类产品止步于"这些词有问题"，不给依据、不给改写、不进工作流。要赢就必须多做后面三步。
4. **单做生成会退化成套壳。** 用户拿 ChatGPT 也能写，只是不知道写完会不会被限流。**"知道会不会"才是他要买的东西。**
5. **合规场景要的是可审计。** 生成是创作行为，检查是判断行为；判断必须能指回条款，否则商家不敢用、面试官也不信。

### 影响（对后续开发的具体约束）

- **D2/D5 必须有"粘贴已有文案直接检查"的入口**：CLI 已支持 `--check`，前端 D5 要给它一个显眼的输入框，而不是只有"生成"按钮。
- **评测集以"检查"为主**：24 条样本衡量的是召回率/误报率/引用正确率；生成只评"人工过稿率"这一项。
- **D3 的"改写"是核心功能，不是附属**：没有改写，用户还得自己想怎么改，价值只兑现了一半。
- **PRD 的一句话定位**：「发布前的合规判断与修订」，而不是「AI 文案生成器」。

### 什么时候该推翻这条决策

- 访谈（D7/D12）中多数商家说"我根本没时间自己写，就要现成的"——那生成权重上调；
- 但即使如此，**检查仍必须保留**，因为它是产品可信度的来源。

### 一句话

> 生成负责"让用户愿意进来"，检查负责"让用户敢发出去"，改写负责"让用户愿意付钱"。

## ADR-002 · 双入口，但「检查」是主路径；不做营销落地页

**日期**：2026-10-24
**状态**：已采纳（对 ADR-001 的细化）

### 背景

ADR-001 定了"检查是内核"，但没有回答一个更具体的问题：
**首页到底先让人干什么？** 最初的设想是「填卖点 → 生成 3 版 → 顺便检查」的三栏工作台。

产品作者提出质疑并说服了设计方，原话大意：

> 如果我们自己生成，那肯定不会违规——因为我们懂平台规范。要查违规，应该是**客户把文案给我们**，我们帮他找问题在哪，顺带生成新方案。

这个判断成立，且比 ADR-001 更锐利：**自产自检是弱闭环**。

### 决策

1. **主入口 = 粘贴检查**：首页视觉重心是一个大粘贴框，按钮是「开始检查」。
2. **次入口 = 生成**：粘贴框下方一行小字「还没有文案？让 AI 先写一版 →」，不抢 C 位。
3. **两个入口进同一个工作台**，只换左栏内容（粘贴文本 / 卖点表单），不写两套 UI。
4. **「顺带生成新方案」= 已有的 rewrite**（按违规项改、保留卖点、给 diff、改完复检），不是新功能，是重新叙事。
5. **不做营销落地页**：产品首屏就是工作入口。介绍性内容交给 README 与 3 分钟视频。

### 理由

- **频率**：商家一天生成 1–2 次、检查 5–10 次——检查才是高频动作。
- **焦虑**：客户真正的痛是"我手上这版能不能发"，不是"再给我十个版本"。
- **省工**：一套工作台 + 两个左栏形态，比两套流程省一半前端工作量。
- **叙事**：对面试官讲"发布前体检"比讲"AI 文案生成器"更清楚、更有差异化。

### 必须补的漏洞

**生成出来的东西并不"必然合规"**（实测：改写把「根治」改成「改善」，仍然违规）。因此：

- 生成模式**仍然要检查**，但定位是"兜底"，不是卖点；
- 生成模式下**右栏不得留空**：要显示「已核 N 条规则，未发现明确违规 + 以下需人工确认（商品资质 / 账号报备 / 图片视频）」，否则用户会以为没检查；
- 对外**不承诺**"我们生成的一定合规"。

### 影响

- 首页、工作台、历史页的信息架构按此实现；
- 评测集以"检查"为主指标（呼应 ADR-001）；
- 生成入口在 UI 上始终是次要动作。

### 什么时候该推翻

若访谈显示商家主要诉求是"我根本没时间写，要现成的"，则提升生成入口权重；但检查能力不得移除。

## ADR-003 · 生成即自检：绝不给用户"挖坑再卖梯子"

**日期**：2026-10-25
**状态**：已采纳（推翻原型中的一个演示设计）

### 背景

原型里为了让"检查→改写"这条链在演示中更明显，我在**促销型草稿里故意留了一句「全网最低」**，选它就能看到违规命中。

产品作者否决，原话大意：

> 我们不可以因为有修改功能，就给用户专门挖坑。他既然用了这个软件，就是信任我们懂条款。如果我们自己生成的东西都可能有问题，那就太说不过去了。生成的东西就要一步到位。

### 决策

1. **生成结果必须是"已自检"的成品**，不得把可能违规的稿子当默认结果展示。
2. 服务端流程固定为：**生成 → 自检（40 条）→ 命中则自动改写（≤2 轮）→ 复检 → 通过才返回**。
3. 自检仍不通过的极少数情况：**标记「需人工确认」并单独呈现**，不得混进正常稿里当成品。
4. 对外措辞只到"**已按 40 条规则自检**"，不承诺"平台一定通过"——判断权在平台，还看账号、图片、视频。

### 理由

- **信任是产品的全部**：用户买的就是"你懂条款"。生成违规再让他修，逻辑上等于承认自己不懂。
- **演示效果不该靠制造缺陷**：这是典型的"为了讲得漂亮而牺牲正确性"。
- **诚实边界靠措辞而非承诺**：可以保证"我们查了 40 条"，不能保证"平台不罚"。

### 技术影响（D5 必须改）

- `POST /api/generate` 内部要跑 `check_text` + `rewrite_draft`，返回体加 `self_check: { rules, fixed, passed }`；
- 生成耗时从约 8s 增到约 15–25s，**前端必须有分阶段进度**（"生成中 → 自检中 → 修复中"），否则用户以为卡死；
- 若 `passed=false`，该版在选稿页显示黄色角标「需人工确认」，不能给「用这版」。

### 什么时候该推翻

若自检+自动修复把成本推到不可接受（如单篇 > 0.3 元或 > 40s），可退回"生成后提示检查"，但**仍然不能把已知违规的稿子当成品**。

## ADR-004 · 工作台三栏语义：原文 | 诊断 | 改写

**日期**：2026-10-25
**状态**：已采纳（推翻 ADR-001 时期的"左输入 / 中正文 / 右列表"设想）

### 背景

最初设想三栏是「输入 → 正文 → 违规列表」，条款要点开一个 480px 抽屉看。
做出原型后发现两个问题：① 检查完左栏（输入）就没用了，白占 300px；② 在 740px 里做"原文 vs 改写"的字符级对比，中文长句会疯狂折行。

参考雅思作文批改工具的形态（正文带下划线 → 中间逐条讲解 → 右侧结果）后调整。

### 决策

三栏固定为：**左＝原文（可编辑，问题处下划线+编号）｜中＝诊断卡（编号/严重度/rule_id/条款原文/建议）｜右＝改写后的全文**。

**连带取消两个组件**：条款抽屉（改为卡片内联展开）、字符级 diff 视图（左右并排即 diff）。

### 理由

- 三栏读起来是一条因果链：**现在是什么样 → 为什么不行 → 改成什么样**。
- 少一个浮层、少一套 diff 算法，前端工作量至少省一天。
- 左栏不再承担"输入"，输入交给入口页，工作台专注"改"。

### 影响

- `frontend/app/workbench/page.jsx` 的三栏结构不得随意改回"列表 + 抽屉"。
- 编号 ①②③ 三栏共用（左栏下划线、中栏卡片、右栏改动处）。

## ADR-005 · 配色：红蓝增删 + 严重度双编码，不引入绿色

**日期**：2026-10-25
**状态**：已采纳

### 背景

设计参考 `DESIGN.md`（Notion 风格）要求"色彩统一"。产品方希望 diff 的红/绿也用它的色号。

**但该调色板里没有绿色**（只有蓝/黄/珊瑚红/棕/深蓝/中性灰）。

### 决策

1. **删除 = `#e32d14` 朱红 + 浅红底 + 删除线；新增 = `#0075de` 主蓝 + 浅蓝底 + 下划线**，两者都在调色板内。
2. **严重度用"颜色 + 线型"双编码**：高危实线 2px / 中危实线 1.5px / 低危虚线 1px；左栏只负责"这里有东西"，真正的标签（高危/中危/低危）在中栏卡片上。

### 理由

- 全部取自 DESIGN.md，满足"风格统一"。
- **红蓝对色弱友好**（红绿色盲最常见，红蓝是安全组合）。
- 三档红色深浅在不同屏幕上几乎不可分，必须加线型差异。

### 影响

- `frontend/app/globals.css` 的 `--del / --add / --high / --medium` 变量是唯一来源，不要在页面里写死色值。
- 若将来要加绿色（如"通过"），需先改写本 ADR。

## ADR-006 · 前端数据层归一化：UI 不得直读后端字段名

**日期**：2026-10-25
**状态**：已采纳（由线上白屏事故促成）

### 背景

mock 数据里改写结果叫 `text`，后端返回叫 `script`。UI 直接写 `rw.text`，接上真接口后 `undefined.indexOf()` 抛错，**整页白屏**——手机端用户实际遇到。

### 决策

1. 所有后端返回在 `frontend/lib/api.js` 里经 `normalizeRewrite` / `normalizeDraft` **归一化成一种形状**；
2. UI 只消费归一化后的形状，**不允许直接读后端原始字段**；
3. 页面渲染再加一层防御（`rw?.text || ""`）；
4. 全局 `app/error.jsx`：出错显示中文提示 + 重试，**不允许黑屏**。

### 理由

mock 存在的意义是"没有后端也能开发"，但它同时制造了"假数据能跑、真数据崩"的盲区。归一化是唯一能同时解决两者的位置。

### 影响

- 新增任何接口字段，先在 `lib/api.js` 归一化，再改页面。
- 审查 PR 时，页面里出现 `res.script`、`res.before_violations` 这类原始字段名即为违规。

## ADR-007 · 线上前端：同源 `/api` + 必须关 mock

**日期**：2026-10-25
**状态**：已采纳

### 背景

首次部署时忘了关 mock，线上跑的是假数据——**页面完全正常，只有规则页显示 7 条而不是 40 条**。这类 bug 不报错，最难发现。

### 决策

1. 部署构建固定 `NEXT_PUBLIC_USE_MOCK=0`、`NEXT_PUBLIC_API_BASE=`（空 → 相对路径，走 Nginx 反代）；
2. 前端与 API **同源**，不存在跨域；CORS 仅用于本地开发；
3. 部署脚本末尾必须做健康检查，且**人工再验证一次"规则页 40 条"**。

### 理由

同源可以消掉一整类 CORS 与端口问题；关 mock 是硬性要求，否则线上是"演示品"而非产品。

### 影响

- 部署后必须核对：`/rules` 显示 40 条、`/health` 返回 `rules: 40`。
- `scripts/deploy.sh` 是唯一部署入口，不要手动 rsync 覆盖。

## ADR-008 · 数字必须来自后端：状态条不写死，后端要算全，还要能对账

**日期**：2026-10-25
**状态**：已采纳（修 B-008 / 原 B1、B2）

### 背景

交接文档把工作台状态条的 `tokens 9,254 / 1,198`、`15.7s` 列为"最危险的已知 bug"——demo 或面试时会被当成真实指标。

真正动手时发现，它比文档描述的麻烦得多：

1. **状态条在工作台，但一次任务跨两个请求**：首页的 `/api/check` + 工作台的 `/api/rewrite`；
2. **那两个接口根本不返回用量**：`check.py` / `rewrite.py` 内部明明算了 `usage`，但 Pydantic 的 `response_model` 会按 schema 裁剪，`CheckResponse` / `RewriteResponse` 里没有这个字段，数字就在接口边界上被吃掉了；
3. **`/api/generate` 的数字也偏小**：只累加了 3 次写作调用，ADR-003 要求的自检、自动改写、复检（每版 3 次额外调用）全没算进去；
4. **`journalctl` 里查不到 token**：`api.py` 没有任何日志，交接文档原本的验收标准（"页面数字与 journalctl 中该次请求的 token 数一致"）**根本无法执行**。

### 决策

1. `/api/generate`、`/api/check`、`/api/rewrite` 一律在响应里返回 `usage`：
   `{tokens_in, tokens_out, latency_ms, elapsed_ms, attempts}`，其中 `tokens_*` 来自模型返回的 `usage`，`elapsed_ms` 是整条请求的墙钟耗时。
2. **`usage` 必须累计该请求内所有 LLM 调用**。改写要算前置检查 + 每一轮改写 + 每一轮复检；生成要算 3 版 ×（写作 + 自检 + 改写 + 复检）= 最多 12 次。
3. 每次请求往 stderr 打**一行**结构化日志，日志器自己挂 handler、不向上传播（不依赖 uvicorn 的 logging 配置）：
   `llm_usage path=/api/check tokens_in=… tokens_out=… llm_ms=… elapsed_ms=… attempts=… draft_id=…`
4. 前端**只消费 `usage`**，不做估算、不设默认值；没有数字就整段不显示。一次任务的显示值是各请求相加（唯一实现在 `frontend/lib/usage.js` 的 `sumUsage`）。
5. 状态条显示的语义是"**本次任务合计**"，不是单次请求的耗时，解释时要说明。

### 理由

- **假数字比没有数字更糟**：没有数字只是信息缺失，假数字会让人误以为链路已被量化，一被追问就崩，还会掩盖"后端压根没算"这件事。
- **唯一知道真实成本的地方是后端**（模型返回的 `usage`）；前端能做的只有"透传"和"相加"。
- **留一行日志是为了能自证**：页面上的数字再准，没有对账手段也说不清。现在一条 `grep llm_usage` 就能和页面数字对上。
- **按请求算、不按任务估**：每个请求自己报自己的账，任务层做加法，任何一层都不需要"猜"。

### 影响

- 新增接口字段时，要么进 `usage`，要么明确声明"本接口不产生模型调用"；页面里再出现写死的 tokens / 耗时即违规。
- mock 数据不含 `usage` → 本地 mock 模式下状态条**没有** tokens 段。这是故意的，不要为了"看起来完整"补一个数。
- 线上旧版仍是写死数字，本次改动要重新部署才生效（见 `handover-D2.md` §6 ②）。

### 怎么验证

- `grep -rn "9,254\|15.7s" frontend/` 无结果；
- 后端测试断言"改写 usage = 前置检查 + 改写 + 复检 3 次调用"、"生成 usage 含自检 12 次调用"；
- 线上对账：页面状态条数字 = `journalctl -u content-guard | grep llm_usage` 中该任务各请求之和。

### 什么时候该推翻

若将来接入多模型路由或 prompt 缓存，`tokens` 的口径要重新定义（缓存命中的部分算不算）。届时先改本 ADR，再改代码。

## ADR-009 · 一次算完：检查、改写、复检在同一个请求里，改动条数 = 违规条数

**日期**：2026-10-25
**状态**：已采纳（推翻 ADR-003 里"先给检查结果、再后台改写"的时序，也推翻"让模型重写整篇"的做法）

### 背景

真实使用中暴露了三个问题，原话：

> 系统只检查出 2 个问题，但是改的时候有三个问题蹦出来，这肯定是不科学的。
> 中间栏的条款原文没有出来，是空的。
> 右边改写的地方…那要让用户自己去找哪里被修改了吗？

根因不在 UI，在流水线：

1. **检查与改写是两个独立请求，改写内部又跑了一次检查**（第二次 LLM 调用）。两次结果本来就可能不同，于是"检查 2 处、改动 3 处"。
2. **「改动明细」直接来自模型自述的 changes**。模型顺手多改一句也不会有人拦，甚至改了什么位置也无法核对。
3. `ViolationOut` 没声明 `clause`，Pydantic 把业务层算好的条款原文裁掉了——数据在 `rules.csv` 里，只是没带出来。

### 决策

1. **新增 `POST /api/analyze`**：解析草稿 → 检查 → 逐条改写 → 复检，**全部算完才返回**。前端只呈现这一份结果，不再有"改写中"的中间态。
2. **改写从「重写整篇」改为「逐条局部替换」**：模型只回答每条违规换成什么，替换动作由服务端执行，并算出替换后的 `start/end`。
3. **改动条数 = 违规条数**，编号 ①②③ 三栏共用。模型没给出可用替换的，标 `unresolved`「未自动改好」，**不编造改动**。
4. **复检结果单独返回**（`remaining` / `after_violations`），页面按真实值显示，不再写死"剩余 0 处"。
5. **改写失败不丢检查结果**：`rewrite_error` 单独返回，页面提示可重试。

### 理由

- **数量一致不是 UI 修出来的，是流水线保证的**：只有"一条违规 → 一个替换"才能让两边严格对齐。
- **位置一致**：模型自述的 diff 不可信（它会改标点、调顺序）；我们自己执行替换，才知道确切位置，高亮不会错位。
- **可审计**：每一处改动都能指回一条 `rule_id` 和一句条款原文，这正是产品的卖点。
- **等得值**：一次 analyze 约 5–10 秒（3 次模型调用），但用户拿到的是一份自洽的结果，而不是"先看一版、再看另一版"。前端显示**真实计时**，不假装进度。

### 影响

- 前端不再有"改写中"状态，工作台只渲染结果；`/api/analyze` 是页面唯一入口。
- `/api/check` 保留（评测、对外接口），但页面不再调用。
- `/api/generate` 的自检与自动改写复用同一套逐条替换逻辑。
- 评测口径要跟着变：不再统计"改动条数"，改为"每处违规是否被修复"。
- 局部替换的代价：句子可能不如整篇重写顺滑。**这是有意的取舍**——可核对优先于文采。

### 验收（2026-10-25 线上实测）

- 4 处违规 → 4 条改动，编号 1:1；每条 `start/end` 切出来的文本与 `after` 完全一致。
- 条款原文与 `source_url` 有值（中栏不再空白）。
- `llm_usage path=/api/analyze … violations=4 rewritten=1` 与响应里的 usage 一致。

### 什么时候该推翻

若局部替换让句子读起来明显生硬（大面积需要重构句子），可以改回整篇改写——但**必须**保留"一条违规 ↔ 一条改动"的映射和人工兜底，否则又会回到"数量对不上"。
