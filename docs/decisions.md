## ADR-001 · 产品内核是「检查与修订」，不是「生成」

**日期**：2026-10-24（D1）
**状态**：已采纳

### 背景

D1 的 CLI 已经能一次生成 3 版文案并逐条检查。由此产生一个必须回答的问题：
这产品到底是"帮商家写文案"，还是"帮商家看文案有没有违规"？

### 决策

**两条腿，但只有一个内核：**

| 层 | 定位 | 作用 |
|---|---|---|
| 入口 A：从零生成 | **获客/体验** | 让"合规"在生成时就发生（护栏前移），而不是事后补救 |
| 入口 B：粘贴已有文案检查 | **主战场** | 商家真实场景：文案多半是手写或改自详情页，不是每次从零生成 |
| 内核：检索 → 检查 → 引用 → 改写 → 确认 | **价值与护城河** | 别家只做其中一段；这里做完整条链且可追溯 |

### 理由

1. **生成不是瓶颈，证据来自自己的实测。** D1 用真实 brief 跑，三版草稿**全部零违规**——说明只要 prompt 里把规则写清楚，模型已经能守住底线。既然如此，"能生成"本身不构成差异。
2. **用户不会为"多生成 10 版"付钱，会为"少改两轮"付钱。**（对应计划 §3.2 假设 2）改一版 20–40 分钟、反复 2–3 轮，这才是成本所在。
3. **单做检查会退化成查词工具。** 零克查词那类产品止步于"这些词有问题"，不给依据、不给改写、不进工作流。要赢就必须多做后面三步。
4. **单做生成会退化成套壳。** 用户拿 ChatGPT 也能写，只是不知道写完会不会被限流。**"知道会不会"才是他要买的东西。**
5. **合规场景要的是可审计。** 生成是创作行为，检查是判断行为；判断必须能指回条款，否则商家不敢用、面试官也不信。

### 影响（对后续开发的具体约束）

- **D2/D5 必须有"粘贴已有文案直接检查"的入口**：CLI 已支持 `--check`，前端 D5 要给它一个显眼的输入框，而不是只有"生成"按钮。
- **评测集以"检查"为主**：24 条样本衡量的是召回率/误报率/引用正确率；生成只评"人工过稿率"这一项。
- **D3 的"改写"是核心功能，不是附属**：没有改写，用户还得自己想怎么改，价值只兑现了一半。
- **PRD 的一句话定位**：「发布前的合规判断与修订」，而不是「AI 文案生成器」。

### 什么时候该推翻这条决策

- 访谈（D7/D12）中多数商家说"我根本没时间自己写，就要现成的"——那生成权重上调；
- 但即使如此，**检查仍必须保留**，因为它是产品可信度的来源。

### 一句话

> 生成负责"让用户愿意进来"，检查负责"让用户敢发出去"，改写负责"让用户愿意付钱"。
